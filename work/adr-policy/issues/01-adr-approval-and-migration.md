# 01: ADRを選別し、本文承認付きで管理できるようにする

## 実現する振る舞い

[変更仕様](../spec.md)に従い、ADRに値する判断だけを草案にし、人間が本文を確認してから
採用する。承認者・日時・本文ハッシュを残し、作業マニフェストがなくなった後も
承認記録と本文の一致をCLIで検査できる。

承認記録のない既存ADRも同じ変更単位で点検・移行し、検証を壊した状態で引き渡さない。
既存文書の削除候補と移行先は適用前に提示し、新ADR本文の承認後に元ADRを削除する。
通常のADR更新は全体置き換えを維持する。

変更仕様のQ1〜Q4・Q6〜Q7・Q9〜Q11を主に扱う。
依存する変更の実装移行・完了を機械的に止める接続は後続チケットで扱い、
このチケットだけで依存関係の検査まで実装済みとは案内しない。

## 依存チケット

なし（すぐに着手可能）。実際の本文採用・元ADR削除には、以下の人間確認が別途必要。

## 受け入れ条件

- [ ] 構造・技術選定・責務分担の判断、有力な代案と実際のトレードオフ、将来必要な選択理由の3条件をすべて満たす場合だけADRを作るプロジェクト規約になっている。
- [ ] 条件を満たさない仕様・運用細則・実装手順の保存先を案内し、代案や理由を創作しない。迷う場合は文書を作る前に候補と理由を短く提示する。
- [ ] 自動生成されるADRは草案であり、会話の設計合意だけで採用済みとせず、毎回人間が本文を確認してからAcceptedにする。
- [ ] 形式の正しい未承認草案はADR検証と調査段階のverifyを通り、形式不正の草案は診断付きで拒否される。
- [ ] 承認者・日時・本文ハッシュをADRのメタデータへ保存し、有効な承認記録と一致する本文をCLIで検査できる。一時マニフェストがなくても検査できる。
- [ ] Accepted表記だけ、承認記録の欠落・型不正・本文不一致は拒否される。人間の読了や記録の真正性をハッシュだけで保証するとは案内しない。
- [ ] 本文変更は誤字・整形・リンクだけでも再承認が必要になる。一覧の再生成と有効な承認メタデータの更新だけでは本文不一致にならない。
- [ ] 既存ADRごとに残す判断・仕様への移行先・削除候補を点検し、適用前に利用者へ提示して確認を得る。
- [ ] 必要な判断を新ADRの草案へ、残りを仕様へ移す。新ADR本文の人間承認を得るまでは元ADRを削除しない。既存のAccepted表記から承認記録を創作しない。
- [ ] 承認後の整理で元ADRを削除し、過去の内容をGit履歴で追える。仕様・判断を欠落させず、残る置き換え参照・本文リンク・一覧を整合させる。
- [ ] 通常の判断変更では継続判断を含む旧ADR全体を後継ADRで置き換える。誤字など意味を変えない修正は本文の直接修正と再承認で扱える。
- [ ] 自己参照・循環・不正な参照・一覧更新漏れの検出を維持し、移行を通すために検証を無効化しない。
- [ ] 実際の一時Gitリポジトリで既存のADR検証・verify CLIを実行し、草案・有効承認・本文変更・不正記録・置き換えを終了コード、診断、一覧とファイル保持で確認する。
- [ ] 現行仕様・テンプレート・エージェント向け指示・利用案内を実装範囲と同期し、意味的な選別と実際の人間確認はレビューで確認する。
- [ ] 独立レビューと必要な文書整理を済ませ、整理後のnpm run verifyが成功する。後続チケットは未完了のまま残す。
