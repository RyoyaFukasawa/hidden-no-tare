# ドメイン文書と設計判断の運用

仕様検討、実装、レビューでは、関連する`docs/product/`の現行仕様を先に読む。
過去の経緯が必要な場合だけ`docs/archive/`を検索する。

用語の定義を共通化する必要がある場合は`CONTEXT.md`へ記録する。作業メモや
一時的な仕様を用語集へ混在させない。

ADRは次の3条件をすべて満たす場合だけ作る。

1. 構造・技術選定・責務分担の判断である。
2. 実際に有力な代案があり、選択にトレードオフがある。
3. 仕様だけでは選択理由が残らず、将来の変更判断にその理由が必要である。

振る舞いと運用細則は現行仕様、実装手順と完了チェックは変更仕様・チケットに記録する。
ADR作成のために代案や比較理由を創作しない。迷ったら文書をまだ作らず、候補と理由を短く確認する。

ADRは`docs/templates/adr.md`からDraftとして作り、`docs/adr/`直下へ全体連番で保存する。
本文を毎回人間が承認するまでAcceptedにしない。設計方針の会話での合意は本文承認ではない。
その判断に依存する本実装は本文承認後に開始し、待機中は調査・試作に限る。
草案の存在だけで無関係な変更を止めない。依存はマニフェストの`adrDependencies`へ記録する。
`artifacts.adr`も依存として検査し、`ready`以降はCLIで未承認の依存を拒否する。申告漏れは指示・レビューで確認する。

採用済み判断の通常の変更は新ADRで旧ADR全体を置き換える。
草案中は旧ADRを維持し、新ADR採用時に旧ADRをSupersededへ変更する。
誤字などの直接修正でも本文の再承認は必要であり、ハッシュだけを更新して確認を省略しない。
機械検査と本文ハッシュの範囲は[現行仕様](../product/exchangeable-development-workflow.md)を参照する。

外部SKILLが別の文書配置を要求しても、長期的な正本はこのプロジェクトの配置とする。
外部成果物から意味を損なわず変換できない情報は、自動的に破棄または補完しない。
