# docs直下の配置を検査するlint

## 課題

`docs/`直下に作業中資料や未知の領域が追加されると、正本の保存先が分散し、文書検証の対象範囲も曖昧になる。

## 解決策

`docs/`直下には`adr/`、`archive/`、`product/`、`templates/`だけを許可する専用lintを追加する。直下の通常ファイル、シンボリックリンク、許可外のディレクトリは検出して失敗させる。作業中の変更仕様とチケットは`.workflow/work/`に置く。

## ユーザーストーリー

1. 開発者として、正本の保存先を一定に保つために、許可外のdocs直下エントリを検証で検出したい。
2. 開発者として、CIとローカル検証で同じ結果を得るために、`npm run verify`からdocs配置lintを実行したい。
3. 開発者として、新規プロジェクトにも同じ規約を適用するために、生成テンプレートへdocs配置lintを含めたい。

## 実装判断

- `scripts/docs-check/check-layout.ts`にdocs直下の通常ファイルとディレクトリを列挙する検査を実装する。
- 許可する直下ディレクトリは`adr`、`archive`、`product`、`templates`の4つに固定する。
- `verify:contract`へ`check-layout.ts`を追加し、通常の`verify`で必ず実行する。
- 同じ検査スクリプトとテストを新規プロジェクトテンプレートへ同梱する。
- 既存のdocs/agentsは許可リスト外のため、参照が必要な情報は正本の4領域へ移管する。

## テスト方針

- 許可された4ディレクトリだけ、直下の通常ファイル、許可外ディレクトリ、シンボリックリンクを一時リポジトリで検証する。
- `npm run verify`がdocs配置lintを実行し、失敗を伝播することを確認する。
- テンプレートから生成したプロジェクトでdocs配置lintが利用できることを確認する。

## 対象外

- docs配下の再帰的なファイル命名規則。
- 既存文書の内容やMarkdown書式の変更。
- 作業資料をGit管理へ追加すること。

## 補足

作業資料は`.workflow/work/<change-id>/`に置き、完了時に必要な変更仕様・チケットだけを`docs/archive/<date>-<change-name>/`へ移管する。
