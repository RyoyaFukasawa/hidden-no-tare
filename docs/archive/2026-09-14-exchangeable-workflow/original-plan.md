# 開発フローと文書管理（導入前メモ）

決定日: 2026-09-14

まずはこの構成で運用し、使っていて不満や手間が見つかったら調整する。
この文書は導入前の検討メモであり、スキルの導入やCIの設定完了を示すものではない。運用時の参照先にはせず、導入時に各ルールを以下の配置先へ移す。移行内容を確認した後、このメモは削除できる。

## 開発フロー

Matt Pocock版のスキルを軸にする。工程の切り替えはユーザーが明示的に指示し、自動連携用の独自スキルは追加しない。

| 工程 | 使うもの |
| --- | --- |
| 仕様・用語・設計判断を詰める | `grill-with-docs` |
| 合意した内容を仕様にする | `to-spec` |
| 検証できる単位に分割する | `to-tickets` |
| 実装する | `implement`＋`tdd` |
| 仕様・品質を確認し、整理する | `code-review` |
| 長い作業を完了まで進める | goal |
| 機械的に検証する | lint・型チェック・テスト・CI |

- 仕様確認時に、受け入れ条件・対象外・テスト範囲・AIに任せる判断を決める。
- タスクは、単独で動作を検証できる小さな機能単位に分ける。
- 実装開始後は、AIがTDD・検証・レビューを進める。Matt版に合わせ、コードの整理はレビュー段階で行う。
- goalには対象の仕様・タスクと、検証可能な完了条件を渡す。
- Superpowersの仕様確認・計画・TDD・実装手順は重複させない。

## 文書の置き場所

当面はローカルMarkdownを基本とし、必要になった文書だけ作成する。

| 保存先 | 役割 |
| --- | --- |
| `AGENTS.md` | 常に守る開発ルール、検証の入口、文書を読む条件 |
| `CONTEXT.md` | 共通の用語集。仕様や作業メモは入れない |
| `docs/index.md` | 現行文書への案内 |
| `docs/agents/` | Matt版の保存先・参照ルールなどの設定 |
| `docs/product/<feature>.md` | 機能ごとの現行仕様 |
| `workflow/docs/templates/product-spec.md` | 現行仕様のテンプレート |
| `workflow/docs/templates/change-spec.md` | 変更仕様のテンプレート。実装判断・テスト方針も含む |
| `workflow/docs/templates/ticket.md` | 実装チケットのテンプレート |
| `docs/adr/README.md` | ADRから自動生成する一覧。ID・タイトル・状態・置き換え元／後継へのリンク |
| `workflow/docs/templates/adr.md` | ADRの記載形式。ADRレコードとしての一覧・番号検証対象から除外 |
| `docs/adr/NNNN-<name>.md` | 重要な設計判断とその理由 |
| skillが選ぶ作業場所 | 作業中の変更仕様・計画・チケット。保存先と分割方法は固定しない |
| `docs/archive/<change>/` | 完了した変更仕様・チケット |

長く残す文書の保存先は`docs/product/`・`docs/adr/`・`docs/archive/`に固定する。作業中の保存先・分割方法はskillに任せる。

`docs/product/`・`docs/archive/`と完了時の整理は、このプロジェクトで追加する運用。Matt版の標準機能だけで自動的に行われるものではない。

## テンプレートの管理

- skillは検討・分割・実装の手順を担い、成果物の形式はプロジェクト側のテンプレートで定義する。skillを将来変更しても、文書の形式を維持できるようにする。
- 初期テンプレートはMatt版と同じ内容でよい。違う形式を作ることではなく、定義と変更の判断をプロジェクト側で持ち、skillへの依存を減らすことが目的。
- 現行仕様は`workflow/docs/templates/product-spec.md`、変更仕様は`workflow/docs/templates/change-spec.md`、チケットは`workflow/docs/templates/ticket.md`、ADRは`workflow/docs/templates/adr.md`を正本とする。実装の設計は変更仕様の実装判断に含め、独立した設計書を毎回追加しない。
- skillの更新・乗り換えだけではテンプレートを変更しない。必要な改善をプロジェクト側で判断して取り込む。
- 導入時にルートの`AGENTS.md`へ、文書作成時は対応するプロジェクトのテンプレートを読み、skill内のテンプレートより優先することを記載する。skillが求める検討事項は対応する項目に反映する。

変更仕様・チケットのテンプレートは作成済み。変更仕様はMatt版の構成・内容を保って日本語化した。チケットは機械処理を簡単にするため、状態をYAMLメタデータの`status`へ移し、本文を固定の日本語見出しに整理した。検証結果欄は初期テンプレートに用意し、完了時の記入を必須とする。ADRテンプレートも作成済み。ADR用lint・一覧生成は`workflow/scripts/adr/`に実装済み。

## 現行仕様の管理

- `workflow/docs/templates/product-spec.md`を作成済み。「目的・範囲」「現行の仕様」「関連文書」の3項目を基本にする。
- 合意した現行の振る舞いを記載し、必要に応じて正常系・境界値・エラーの具体例を添える。単純なルールは文章だけでよい。
- 判断の経緯はADR、実装手順・完了チェックは変更仕様やチケットに置く。重複する説明はリンクで参照する。
- 仕様を変更するコードと同じPRで更新する。不具合に合わせて仕様を書き換えない。
- 関係ない項目は増やさず、固定のチェックボックスや状態・担当者・更新日のメタデータは設けない。

## AIへのルールの読み込み

導入時はルートの`AGENTS.md`に読む条件と参照先だけを記載し、詳細は`docs/agents/domain.md`へまとめる。`docs/adr/AGENTS.md`は追加しない。

```markdown
## 設計判断・ADR

- 用語・設計判断の検討、またはADRの作成・変更時は、
  docs/agents/domain.mdを先に読む。
- 関連する設計判断はdocs/adr/README.mdから確認し、
  ADR作成時はdocs/templates/adr.mdを使う。
- ADR変更後は一覧を再生成し、ADR用lintを実行する。
```

Matt版のセットアップにはドメイン文書への参照を追加する導線があり、`grill-with-docs`は内部で`domain-modeling`を使う。ただし、ファイルを置くだけで必ず読まれるとは考えず、上記の参照指示で読む条件を明示する。

AIはルートの`AGENTS.md`を入口に、仕様検討・実装・ADR更新の必要な場面で詳細ルールを読む。これは指示による読み込みであり、機械的な強制ではない。形式・状態・参照関係の抜けはlintで補う。

`docs/agents/domain.md`には、次の運用ルールを移す。

- 用語集と関連ADRを読むタイミング、既存判断と矛盾した場合の扱い。
- `CONTEXT.md`を用語集に限定し、定義の確定・変更時に更新すること。
- ADRの作成条件・保存先・採番・状態・ユーザーによる採用判断。
- 判断を一部でも変更する場合は新ADRを作り、継続する判断も含めて旧ADR全体を置き換えること。
- 誤字修正や判断の意味を変えない補足は既存ADRを直接修正できること。
- `supersedes`による置き換え、旧ADRの保持、適用終了時の理由の記録。
- 更新後のREADME再生成・lint実行・関連する現行仕様の更新。

ADRの具体的な記載形式は`workflow/docs/templates/adr.md`、機械的な検証は自作スクリプト・CIへ移す。READMEは自動生成する一覧に限定し、手書きの運用ルールを置かない。
Matt版のスキル本体は改造せず、プロジェクト固有のADR規約を優先することを`docs/agents/domain.md`に明記する。導入時に実際の生成・検証コマンドを上記の案内へ追記する。

## 文書を増やしすぎないルール

- 現行仕様は機能ごとに正本を1つにし、変更時は既存文書を更新する。
- 同じ変更の再相談では既存の変更仕様を更新する。版の履歴はGitで管理する。
- 仕様・チケット・継続に必要な記録はGitに保存する。`.scratch/`を名前だけで一括除外しない。
- goalの進捗・検証結果は既存チケットに記録し、毎回別の報告書を作らない。
- 同じ説明を複製せず、正本へのリンクを使う。
- ADRは「変更コストが大きい」「理由が自明でない」「代替案を比較した」の3条件を満たす判断だけ残す。短い文章でよい。
- AIは作業に関連する現行文書から読み、アーカイブは経緯の調査が必要なときに参照する。

## 完了した変更文書の保存

- 合意した変更仕様・チケットは削除してGit履歴だけに残す方式ではなく、`docs/archive/<change>/`へ移動し、Gitにコミットする。clone後に通常の検索で経緯を調べられることを優先する。
- `<change>`は`2026-09-14-add-payment`のような日付と変更名とし、チーム共通で変更単位に整理する。個人別には分けず、同じ変更を複数人で担当しても1フォルダにまとめる。
- 既存の変更仕様・計画・完了チケットを移動し、アーカイブ用の報告書を新たに作らない。仕様・計画の分割は維持してよい。機械検証のため、完了チケットは`docs/archive/<change>/issues/`にまとめ、チケットテンプレートの形式に揃える。未完了チケットは作業場所に残す。会話ログ・重複した下書き・一時メモは、必要な情報を現行仕様・ADR・チケットへ反映した後に削除する。
- 実装・検証・レビュー後、現行仕様の更新とアーカイブへの移動をコードと同じPRに含める。PRレビューで内容が変わった場合は文書も修正する。
- アーカイブは当時の記録として保持し、現在の仕様に追従させない。AIは現行仕様・関連ADRを先に読み、過去の経緯が必要な場合だけアーカイブを検索する。この参照順序を導入時にルートの`AGENTS.md`へ記載する。
- PRにはレビューの会話・検証結果を残す。仕様・判断の保存をPRだけに依存させない。

## ADRの管理

- ADRは機能・ドメイン別に分割せず、`docs/adr/`直下に全体連番で保存する。判断が複数の機能・ドメインにまたがるため、保存先を一本化する。
- 適用範囲はADR本文に自然な言葉で記載し、機能の現行仕様から関連ADRへリンクする。分類の判断を増やさないため、`areas`は設けない。
- 各ADRの状態を正本とし、`docs/adr/README.md`はADRから自動生成する。一覧の状態や置き換え関係を手入力しない。
- 状態は `Accepted`（採用済み）、`Superseded`（別ADRに置き換え済み）、`Deprecated`（後継の判断を伴わず適用終了）の3つに限定する。採用済みと実装完了は区別し、移行中なら適用時期や実装チケットを記載する。
- 提案者はユーザーとし、ADRにはユーザーが採用を決めた判断を`Accepted`として記録する。検討中の案は会話や変更仕様で扱い、不採用の選択肢は必要に応じて採用したADRの理由に記載する。
- 採用済みの判断を変える場合は、ユーザーが新しい判断を採用した時点で、新しい番号のADRを追加し、旧ADRを`Superseded`にする。
- 判断を一部でも変更する場合は、新ADRに継続する判断も含め、旧ADR全体を置き換える。誤字修正や判断の意味を変えない補足は既存ADRを直接修正できる。
- 後継なしで適用を終了する場合は、ユーザーの判断で`Deprecated`にし、終了理由を本文に記載する。
- 置き換え関係は新ADRの`supersedes`に置き換え元のIDだけを記録する。後継は全ADRの`supersedes`から逆算し、READMEに両方向のリンクを生成する。`superseded_by`は記載しない。
- 旧ADRの判断・理由と既存の`supersedes`は保持し、状態を更新する。後継がさらに置き換えられても直接の関係を残し、判断の経緯を追えるようにする。
- 置き換え済みのADRも同じディレクトリに残し、番号の再利用や`v2`形式の複製はしない。

## ADRテンプレート

ファイル名は`NNNN-<name>.md`。内容検索でも見つけられるように、最初の見出しを`# ADR-NNNN: タイトル`とし、IDをMarkdown内にも記載する。ファイル名と見出しのIDが一致することをlintで検証する。YAMLにはIDを重複して持たない。

````markdown
---
status: Accepted
---

# ADR-0001: 判断を表す短いタイトル

## 背景

判断が必要になった理由と、適用する範囲。

## 決定と理由

採用した判断と理由。必要なら比較した選択肢も記載する。

## 影響

制約やトレードオフ。移行が必要なら適用時期や実装チケットへのリンク。
````

本文の見出し構成は推奨であり、短いADRでは1段落にまとめてもよい。
既存ADRを置き換える場合だけ、新ADRのYAMLに`supersedes`を追加する。

```yaml
---
status: Accepted
supersedes: ["0002"]
---
```

- `status`は必須。値はADRの管理で定めた3種類に限定する。
- `supersedes`は4桁のID文字列の配列とする。先頭のゼロを保つため引用符で囲む。
- 複数の判断を統合する場合は`supersedes: ["0002", "0005"]`のように記載できる。
- 置き換え元がなければ`supersedes`自体を省略する。
- この例なら旧ADR-0002の状態を`Superseded`に変更する。後継の0003などのIDを旧ADRへ手入力する必要はない。

## ADR用lintの導入方針

- [x] ADR固有の整合性検証と一覧生成を`workflow/scripts/adr/`に実装し、`verify`に組み込んだ。既存CIは`verify`を実行するが、CI上の動作確認は未実施。

Markdownの書式は`markdownlint-cli2`、リンク切れは`lychee`を使用し、自作部分はADR固有の検証と一覧生成に絞る。

| チェック対象 | 検証すること |
| --- | --- |
| 保存先・ID | ADRが指定場所・命名規則に従い、番号が重複していない。最初の見出しが`ADR-NNNN: タイトル`形式で、IDがファイル名と一致する |
| ADR本体 | 状態とタイトルが存在し、状態が定義済みの値である。`supersedes`がある場合は、重複のない4桁ID文字列の非空配列である |
| README一覧 | すべてのADRが1回ずつ掲載され、リンクが実在し、ID・状態がADR本体と一致する |
| 状態と後継 | 他ADRの`supersedes`から参照されるADRは`Superseded`であり、`Superseded`のADRには逆算できる後継が1件以上ある |
| 置き換え関係 | `supersedes`の参照先が実在し、自己参照・循環参照がない。READMEの置き換え元／後継リンクが算出結果と一致する |

生成結果とコミット済みREADMEの差分をCIで検出する。Markdownの書式チェックだけで、状態・後継関係の検証を代替しない。
判断の内容や置き換えの妥当性はAI・人間のレビューで確認する。ADR用スクリプトは実装済み。Markdown書式・リンクチェックは設定とCIへの組み込み済み。ただしローカルの依存インストールはディスク容量不足で失敗し、実ツールでの動作確認は未完了。

一覧生成は`npm --prefix workflow run adr:generate`、単独検証は`npm --prefix workflow run adr:check`。検証は読み取り専用で、不整合時には生成も既存一覧を更新しない。メタデータはテンプレートどおりの`status: Accepted`形式と、任意の`supersedes: ["0002", "0005"]`形式に限定する。一般のYAML構文には対応しない。

## Markdown・リンクチェック

- `workflow/scripts/docs-check/`に実行スクリプトと設定をまとめる。Markdownは`markdownlint-cli2`、リンクは`lychee`を使用する。
- 対象はルートの`AGENTS.md`、`workflow/`直下のMarkdown、`workflow/docs/`、`docs/product/`・`docs/adr/`・`docs/archive/`。既存の調査メモやskill独自の作業場所は対象外。
- `npm --prefix workflow run lint:md`と`npm --prefix workflow run lint:links`を`verify`で実行する。リンク検証はオフラインでファイル・見出しへの参照を確認し、外部サービスの応答には依存しない。
- 外部URLも含む検証は`npm --prefix workflow run lint:links:online`。書式・リンクの検証では文書を自動修正しない。
- ローカルではnpm依存に加えてlycheeが必要（macOSでは`brew install lychee`）。CIではlychee 0.24.2をインストールする。

## 完了条件

機械判定する完了条件は`workflow/scripts/completion-check/completion.ts`に集約し、Markdownを読む`workflow/scripts/completion-check/check-work-items.ts`から分離する。使用するskillにかかわらず同じ契約・検証入口を使う。skillの乗り換えで完了条件を変更しない。

以下をAIの完了作業に含める。文書整理のためにユーザーが毎回別の指示を出す運用にはしない。

- 受け入れ条件を満たし、必要な検証が成功している。
- 仕様適合とコード品質をレビューし、重大な指摘を解消している。
- 振る舞いを変更した場合は、対応する現行仕様を更新している。
- 必要に応じて用語集・ADRを更新している。
- 残課題をチケットへ引き継ぎ、完了した作業文書をアーカイブしている。
- 文書の移動に伴うリンクを更新し、一時メモの重要情報を適切な文書に移している。

完了チェッカーはアーカイブ後のチケットだけを対象とし、作業中の保存先は走査しない。アーカイブへの移動漏れ自体は検出できないため、レビューで確認する。

## 検証の分担

チケットの完了ガードはTypeScriptで実装し、テンプレート・規約・スクリプト・テストを`workflow/`に集約した。ルートの`AGENTS.md`は`workflow/AGENTS.md`への案内にする。運用の指示は[AGENTS.md](../../../AGENTS.md)に記載し、ルート`AGENTS.md`から参照する。`npm --prefix workflow run verify`がworkflowの型チェック・回帰テストと`docs/archive/<change>/issues/**/*.md`の完了チケット検証とADR検証を実行する。GitHub Actionsの設定ファイルも追加済みだが、リモート未設定のためCI上の実行確認とマージ必須チェックの設定は未実施。以下のうち、アプリの検証は引き続き導入予定。文書チェックの設定は追加済みで、依存導入と実行確認が残っている。

- **機械:** lint・型チェック・テスト・ビルド、文書の形式・内部リンク・ID重複などを検証する。検証の入口を`verify`にまとめ、CIでも実行する。
- **AI:** 検証の実行と修正、仕様の抜け、文書の重複、コードと文書の矛盾を確認する。
- **人間:** 仕様・優先順位・使いやすさを判断する。

コードと文書が矛盾した場合は、受け入れ条件とテストを照合する。コードに合わせて無条件に文書を書き換えない。未実行の検証は未実行として報告する。
