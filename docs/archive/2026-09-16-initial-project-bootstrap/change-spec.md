# 新規プロジェクト向け初期セットアップCLI

## 課題

現状はこのリポジトリをテンプレートとしてcloneし、手動で初期環境を整える必要がある。別プロジェクトで同じ開発ワークフローを使うときに、生成物の不足や途中導入を誤って許可する危険がある。

## 解決策

公開npmパッケージの`create-project-work-flow`として提供する。新規Gitリポジトリだけを受け付け、`npm create project-work-flow@<version>`でCLIを実行する。生成物を一時領域で検証してから安全に展開し、生成物の所有マニフェストを使って再実行と、実行したnpmパッケージ版による更新で利用者の変更を保護する。

## ユーザーストーリー

1. 開発者として、新しいGitリポジトリで同じ開発ワークフローを使い始めるために、初期セットアップCLIを実行したい。
2. 開発者として、npmまたはpnpmを選んでNode.js基盤と検証入口を準備したい。
3. 開発者として、生成前に変更内容を確認し、失敗時にリポジトリへ部分的な変更を残したくない。
4. 開発者として、初期セットアップ後に自分で差分を確認してコミットしたい。
5. 開発者として、同じ版の初期化を再実行しても安全に扱いたい。
6. 開発者として、固定版のnpmパッケージからフレームワーク所有ファイルだけを明示的に更新したい。
7. 開発者として、既存コードのあるリポジトリへ誤って途中導入しないよう、CLIに停止してほしい。

## 実装判断

- npm create互換の`create-project-work-flow`パッケージと`project-work-flow` CLIを作る。
- CLIはNode.jsで動作し、導入先アプリの言語には依存しない。
- npmの公開レジストリから固定版を指定して実行できる。
- ルートに許可される既存ファイルは`.gitignore`と`README.md`だけとし、GitのHEADを必須にする。
- CLI引数を優先し、未指定の値だけ対話で入力する。プロジェクト名はディレクトリ名を初期値にする。
- パッケージマネージャーはロックファイルを自動検出し、検出できない場合はnpmまたはpnpmを質問する。
- `--install`が指定された場合だけ依存関係を導入する。コミットは作成しない。
- 既存の`.gitignore`へ追記する場合は差分を表示し、`--accept-existing`の明示指定後だけ追記する。
- 生成物は一時領域で準備し、検証成功後に適用する。`--dry-run`は適用せず予定だけ表示する。
- `.workflow/setup-manifest.json`に版、所有ファイル、ハッシュを記録する。更新はこの所有情報を使う。
- 初期化・更新は所有ファイルの変更と新規パスの衝突を検出したら停止し、既存の利用者ファイルを上書きしない。
- `projectChecks`は空配列で生成し、アプリ固有の検証接続は利用者の作業とする。

## テスト方針

- CLIプロセスを公開境界として実行し、終了コード・標準出力・ファイルシステムの結果を検証する。
- 新規Gitリポジトリ、許可されたREADME/.gitignore、未コミット、許可されない既存ファイル、再実行、更新、dry-run、失敗時ロールバックを一時fixtureで確認する。
- npmとpnpmの検出・明示選択、および`--install`の有無を確認する。
- 固定版npmパッケージの実行境界で初期化・更新・生成後verify/workflow:prepareを確認する。
- テストは実装内部の関数やモックではなく、利用者が観測できる初期化・更新の振る舞いを検証する。

## 対象外

- 既存コードがあるプロジェクトへの途中導入、自動マージ、自動上書き。
- 外部SKILLや接続の自動導入。
- 多人数向けの運用支援、言語別の専用アダプター。
- 利用者のGitコミット作成、アプリ固有の`projectChecks`設定。

## 補足

完了時には初期セットアップの仕様、対象外、CLI契約、生成物、検証結果をアーカイブへ移管する。
