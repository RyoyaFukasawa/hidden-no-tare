# 交換可能な開発ワークフロー

## 目的・範囲

外部の開発SKILLやエージェントを交換しても、ソフトウェア開発で長く残す
成果物と完了条件を維持する。本仕様はコード、関連仕様、ADR、運用設定を扱う。
外部SKILLの判断品質や完全な安全性は保証しない。

## 現行の仕様

### 責務の分離

外部ワークフローは調査、要件定義、計画、実装、レビューの手順を担う。
プロジェクトは現行仕様、受け入れ条件、検証証跡、未確認事項、完了文書の
保存契約を担う。フロー全体、フェーズ、個別SKILLのいずれも交換できる。

変更マニフェスト、変更分類、リスク、必要成果物、レビューは必須である。
外部SKILLの登録、認証、比較実験は任意であり、削除・交換しても通常の検証は動く。

エージェント固有の指示ファイルは接続方法だけを記載する。機械可読な設定、
成果物テンプレート、検証CLIを正本とする。

### 変更のライフサイクル

変更ごとに独立したマニフェストを持ち、並行作業は別worktreeで行う。開始時の状態は
`researching`とする。エージェントが変更特性を推定し、高リスクまたは不確実な
項目だけを利用者へ確認する。

未分類の項目がある間は、調査、テスト、影響分析、試作だけを許可する。
本実装と完了には進めない。通常扱いでは完了時に必要な情報をチケットと証跡へ統合し、
作業マニフェスト自体は長期保存しない。軽微変更の理由・検証結果・レビューは
一時マニフェストで管理し、代替の長期文書は作らない。

prepareの必須入力は変更IDと概要だけ。外部ワークフロー情報は省略できる。
設定・マニフェストのJSONは実行時に型、必須項目、未対応の項目を検証する。
ready以降には全変更特性とリスクの確定、および分類確認を要求する。

### 必要成果物

通常扱いの変更にチケットを要求する。利用者向けの振る舞いを変更する場合は
現行仕様と変更仕様を要求する。ADRの3条件に該当する判断を新たに採用・変更する場合は
`architectureDecisionChanged: true`とし、ADRを要求する。単に仕様の細則を変更しただけでは
この特性をtrueにしない。意味的な該当判定は指示・独立レビューで確認し、CLIは申告された
変更特性から必要成果物を導出する。成果物の要否は外部SKILL自身の完了宣言に委ねない。

軽微変更に限りチケットとそのアーカイブを省略できる。対象は動作や仕様の意味を
変えない誤字・コメント・整形だけで、リファクタリング、不具合修正、高リスク変更は含めない。
低リスクや少ない行数だけでは軽微変更にしない。
チケットの作成負担を減らしても、作業状態と分類の管理を失う必要はないため、
一時マニフェストまで省略しない。

軽微変更はマニフェストの`lightweight: { reason: "分類理由" }`で宣言する。
宣言がなければ従来形式を含め通常扱いとする。理由は空白だけでは不可。
高リスク、非空の高リスク分類、trueの変更特性と宣言が矛盾する場合は拒否する。
完了時は既存の分類確定条件に加え、`review.lightweightConfirmed: true`を要求する。
独立レビュー担当が差分と分類理由を確認した場合だけ記録し、実装担当が代わりに確認済みにしない。
意味の同一性や担当者の独立性はCLIが自動判定するものではない。

迷う場合や独立レビューで否定された場合は`lightweight`を削除して通常扱いへ戻し、
変更特性・リスクを再評価してチケットを含む必要成果物を用意する。古いレビューは
破棄して再検証・再レビューする。例えば「必須」を「任意」に変える修正は、
一語でも仕様の意味を変えるため通常扱いになる。
全変更のマニフェスト・verify・レビュー・Git状態の検査は維持し、
チケット省略の都度の人間承認は追加しない。

外部ワークフローの成果物は中間生成物として扱う。標準成果物へ損失なく変換
できない情報があれば完了を止め、利用者が配置または破棄を判断する。

### ADRの選別と本文承認

ADRは次の3条件をすべて満たす判断だけに作る。

1. 構造・技術選定・責務分担の判断である。
2. 実際に有力な代案があり、選択にトレードオフがある。
3. 仕様だけでは選択理由が残らず、将来の変更判断にその理由が必要である。

振る舞い・運用細則は現行仕様、実装手順・完了チェックは変更仕様やチケットへ記録する。
ADRを作るために代案や理由を創作しない。迷う場合は文書をまだ作らず、候補と迷う理由を
短く提示して利用者に確認する。過去にADRに書かれていたこと自体を、残す理由にしない。

自動生成時は`Draft`とする。人間が実際の本文を毎回確認・承認してから`Accepted`にする。
会話での設計合意だけでは本文承認にならない。未承認の判断に依存する作業は調査・試作まで。
その判断に依存する本実装は本文承認後に開始する。無関係な有効草案があるだけでは、
別の変更を止めない。ADRの選別と実際の読了は指示・人間確認・独立レビューで確認する。

ADRメタデータは`status`、任意の`supersedes`と次の3項目を受け付け、未知キー・重複キーは拒否する。
一般的なYAML構文ではなく、テンプレートの形式だけを受け付ける。

| フィールド | 値 |
| --- | --- |
| `approvedBy` | 制御文字を含まない空でないJSON文字列。承認した人を記録する |
| `approvedAt` | JSON文字列の実在するUTC日時。秒まで、またはミリ秒3桁付きのISO形式 |
| `approvedBodySha256` | JSON文字列の小文字64桁SHA-256。人間が承認した本文を対象にする |

`Draft`には承認3項目を付けない。`Accepted`・`Superseded`・`Deprecated`にはすべて必須であり、
状態だけの変更、承認記録の欠落・型不正・不正日時・本文不一致をADR検証で拒否する。
承認記録は一時マニフェストにだけ残すのではなく、ADRとともに永続化する。
本文変更時にハッシュだけを更新して人間確認を省略してはならない。

ハッシュの本文範囲は、先頭frontmatterの終了行`---`に続く改行の直後からファイル末尾まで。
UTF-8の本文をそのままSHA-256にし、先頭空行、末尾改行、コメント、空白、CRLFを正規化しない。
誤字・整形・リンクを含むすべての本文変更で再承認が必要になる。ADR一覧の再生成と
有効なメタデータの更新は本文を変えない。ハッシュは読了や承認者の真正性を証明する電子署名ではない。
実際に本文承認を得たことは、人間確認と独立レビューで確認する。

通常の判断変更では、新ADRに継続する判断も含めて元ADR全体を置き換える。
新ADRの`supersedes`は実在する非DraftのIDを非空配列で指定する。草案中は置き換えの提案であり、
旧ADRをまだ失効させない。新ADRの採用時に旧ADRを`Superseded`にする。
生成一覧の草案行の置き換え元は提案を表し、後継欄には草案を含めない。
自己参照・循環・不存在参照・状態と正式な後継の不一致・一覧更新漏れは拒否する。
判断の意味を変えない直接修正は許可するが、本文の再承認は省略しない。

既存ADRを整理するときは、残す判断・仕様への移行先・削除候補を適用前に提示する。
混在した文書からADRに値する判断を新しい草案へ、残りを仕様へ移し、新本文の承認後に元ADRを削除する。
一度きりの文書整理と通常の全体置き換えは区別する。削除対象への参照を残さず、
過去はGit履歴で追う。既存のAccepted表記から承認記録を創作しない。

ADR単体の形式・承認検査は`adr:check`と通常の`verify`に含まれる。有効草案の形式検証は成功する。
変更マニフェストの`adrDependencies`には依存するADRの4桁IDを文字列配列で宣言する。
省略または空配列は追加の依存なしを表す。型不正・4桁以外・重複・存在しないIDを拒否する。
`artifacts.adr`も依存に含めるため、配列から省いても検査される。この成果物は
`docs/adr/NNNN-<name>.md`の正規パスで指定し、別の文書や別名パスによる代用は拒否する。
`architectureDecisionChanged: true`では`ready`以降、ADR成果物の指定が必須になる。

`unclassified`・`researching`では形式の正しい依存草案を許可する。
`ready`を本実装へ移行可能な状態とし、`ready`・`implementing`・`review`・`complete`では
依存する草案を拒否する。非Draftの承認記録・本文一致・置き換え関係はADR単体と同じ検査を利用する。
有効な過去の承認記録も検査できるが、旧判断への依存が意味的に適切かはレビューで確認する。
承認不備や本文不一致は調査中でも拒否し、無関係な有効草案は他の変更を止めない。
依存を使った検査は`verify:contract`・`verify`・`workflow:finalize`に含め、
プロジェクト検証後にも再確認する。依存の申告漏れは指示・独立レビューで確認する。
CLIを通さない編集の物理的禁止や、人間の読了の自動証明は保証しない。
高リスク変更の最終コミット承認も維持し、ADR本文承認と混同しない。

### リスクとレビュー

共通の高リスク分類は、認証・認可、秘密情報と暗号、決済、個人情報、不可逆な
データ変更、公開APIの破壊的変更、セキュリティ境界、本番インフラ、法的同意、
完了判定、サプライチェーンである。プロジェクトは分類を追加できるが削除できない。

通常変更は独立したレビュー担当エージェントでも承認できる。高リスク変更は
人間の承認を必須とし、承認者、UTC日時、対象Gitコミットを記録する。対象差分が
変われば承認を失効させる。Gitを必須とする。

検証・独立レビュー・文書整理を済ませてコミットし、そのSHAを承認対象にする。
承認後は検証済みの未追跡一時マニフェストだけを更新する。コード・文書の変更には再承認を要求する。
完了状態ではHEAD比較に加え、staged・unstaged・untracked変更を拒否する。
通常のGit ignore対象と、有効な未追跡の`.workflow/changes/<id>.json`だけを除外する。
追跡済みマニフェストは完了前に追跡から外し、その変更を含むコミットで承認を受け直す。
レビュー中のverifyは開発用検証であり、最終承認や完了の代わりにはならない。

### 検証

`verify:contract`は成果物、証跡、承認、状態、ADR、文書を検査する。
`verify:project`は設定されたアプリ固有のコマンドをシェル展開なしで実行する。
`verify`は両方を呼ぶ唯一の完了入口である。検証器の例外、ツール不足、未実行、
証跡不足は成功として扱わない。

verifyとfinalizeはプロジェクト検証後にも完了境界を再確認する。検証中に生じた
未コミット変更や、開始時の完了マニフェストの書換え・削除は成功扱いしない。
finalizeは検証成功後だけ対象の一時マニフェストを削除する。

### 緊急例外

緊急例外には、人間の承認、理由、後続チケット、解消期限を要求する。期限は
既定7日、最大30日とする。期限を超過した未解消例外があれば完了を拒否する。

### 外部ワークフローとアダプター

汎用アダプターを標準とし、独自形式を要求する外部ワークフローだけ個別
アダプターを追加する。アダプターはパス、形式、ライフサイクルを機械的に接続し、
要件や受け入れ条件を創作しない。

外部SKILLは出所、ライセンス、固定コミット、要求権限、危険な命令を検査する。
認証済みとは、指定バージョンとの接続、変換、停止条件、完了契約を正常系、
失敗系、敵対的ケースで確認済みという意味である。

任意の`verify:registration`で作業マニフェストが`workflow.certified: true`を宣言する場合、登録検証は
`adapters/*.json`の有効な記録から指定IDを一度だけ読み、その記録が
`certified`状態であり、外部ワークフローの固定コミットが
`workflow.version`と一致することを要求する。ID不存在、候補状態、固定コミット
不一致は個別にエラーとする。`certified: false`はアダプター記録なしでも利用できる。

Matt Pocock版の`grill-with-docs`、`to-spec`、`to-tickets`、`implement`、`tdd`、
`code-review`とSuperpowersは任意の利用例として同梱する。利用例の比較実験は
`verify:examples`でだけ実行し、通常のverify・型検証・テストは固有のファイルを要求しない。
通常のverifyが成功しても外部ワークフローの認証済みを意味しない。

### 導入対象と実行環境

新規リポジトリを正式な導入対象とする。Node.js、Git、外部リンク検証ツールを使用し、
必要版と導入方法はREADMEに示す。ツール不足は導入案内付きで失敗させる。
既存向けdiagnoseは6ファイルの限定比較とし、対象と未検査範囲を出力する。
衝突がないことを安全な導入と呼ばず、既存ファイルを自動マージ・上書きしない。
